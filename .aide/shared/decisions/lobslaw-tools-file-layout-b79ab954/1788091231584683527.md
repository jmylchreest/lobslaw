# lobslaw-tools-file-layout

**Decision:** internal/tools is one file per tool, named for the tool. Shared machinery carries a lib_ prefix. A file is one or the other.

## Rationale

A prefix only carries information when it marks the minority. The previous builtin_ prefix marked 30 of 37 files and so distinguished nothing, which is why the registry and the guard chain sat unnoticed between binaries.go and session.go. The split that matters is blast radius at review time: a change under lib_ moves the floor for every tool, where a change to pdf.go moves one.

## Details

Tool file: <tool>.go holds that tool's ToolDef, handler and config together — the model-facing description and the code that runs must not drift apart in separate files.
Machinery: lib_registry.go (catalogue, disabled-tool globs, recommend/avoid cross-refs), lib_builtins.go (in-process dispatcher), lib_guard.go + lib_mounts.go + lib_landlock.go (the mount -> hardline -> policy.d chain every path-taking tool runs).
A helper private to one tool takes that tool's name, not lib_ — remote_transport.go, not lib_ssh.go. lib_ means shared by many tools.
Enforced by TestMachineryFilesDeclareNoTools, which fails if a b.Register appears in a lib_ file. The drift this catches is someone adding a tool to the file that already has the registry open, where an extra registration is least likely to be noticed.
Applies to filenames only. Package names stay short and underscore-free per go-project-structure.
