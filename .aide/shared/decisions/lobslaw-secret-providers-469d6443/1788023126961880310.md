# lobslaw-secret-providers

**Decision:** Secret references resolve through a provider registry — the same driver waist chat, vision, audio, image and search already use. A provider's config LABEL is the reference scheme, so `bw:app/key` works anywhere `env:APP_KEY` does. Two tiers: compiled drivers (bitwarden, onepassword) for backends whose failure modes need translating, and `exec` for any CLI, which covers pass/gopass/sops/age/systemd-creds with no Go. Transport is the vendor CLI rather than the vendor API, because an API-backed provider moves one secret onto disk to take another one off it. env: and file: are a reserved bootstrap floor that no provider may shadow: memory.encryption.key_ref, [cluster.mtls] and any provider's own credential resolve before a provider can exist.

## Rationale

`pkg/config/secret.go` was the whole surface: `env:VAR` or `file:/path`, both resolving against the node's own machine. Every provider key and channel token was therefore provisioned per node, rotated by hand, and readable by anyone who could read the filesystem the sandbox exists to protect. `HERMES_GAPS.md` 6.1 calls this the more urgent of the two Tier 6 items precisely because it is a security posture gap rather than a feature gap: it gets worse with every node added and every new key.

`kms:` was advertised as a supported scheme in **seven** places across code comments and developer docs and had never been implemented. That is the fourth instance this week of documentation describing a capability nobody wrote, after `provider = "tavily"`, the `web_search` egress role, and a "runtime edits via builtins" comment justifying behaviour around a builtin that does not exist. The corrections ship with this change.

**Why the label is the scheme.** References stay `scheme:rest`, exactly the shape every `_ref` field already takes, so nothing above the resolver has to learn a new syntax. It also means the set of legal schemes is visible in one place in config rather than compiled in.

**Why two tiers.** `bitwarden` and `onepassword` could both be `exec` blocks — `command = ["bw", "get", "password", "{{path}}"]` works. They earn a file each for the reason the SearXNG search driver did: the common failure is a locked vault or an expired session, the CLI says something that means nothing on its own, and the fix is a specific command. "exit status 1: mac failed" is an afternoon; "run `bw unlock` and export BW_SESSION" is five seconds. The hint is *added* to the CLI's own output, never substituted for it, so guessing wrong about which failure occurred cannot hide what actually happened.

**Why the CLI and not the API.** Both vendors offer one, and both require their own access token — which would itself have to be bootstrapped from `env:` or `file:`. An API-backed provider moves one secret onto disk to take another one off it. The CLI reuses the session or service account the operator already has.

**Why `exec` is acceptable.** It runs an arbitrary command from `config.toml`. `[mcp.servers.<name>]` already takes a `Command` and `Args`, and a skill manifest already takes an `Install` argv — both arbitrary commands from that same file, both spawned at boot. Anyone who can edit it can already run code as the node, so this extends no trust that has not already been extended. It must not *widen* it, which is why it takes an argv and never a shell string: a secret path containing a space must not be able to become a second command.

**Why the bootstrap floor is not negotiable.** `cmd/lobslaw` resolves `memory.encryption.key_ref` before `node.New`, so before any wiring stage — including the one that would build a provider — exists. mTLS paths are read the same way. And a provider whose own credential came from another vault needs one of them working before either does. This is an ordering fact, not a policy, so the floor is enforced with an error that explains it rather than reporting an unknown scheme.

## Consequences

- Adding a backend is one file and one `Register` line, or a TOML block with no Go at all.
- `lobslaw doctor` resolves a *real* reference through each provider rather than only constructing it. Constructing proves nothing: a missing binary, a locked vault and an expired session all construct fine and fail at the first fetch, which on this node is during boot.
- Resolved values are cached for 5 minutes by default. One boot resolves the same reference several times — chat driver, capability probe, doctor — and each would otherwise be a separate process.
- Rotation is explicitly out of scope. Secrets resolve at boot into constructed drivers, so re-resolving without rebuilding them changes nothing; that is a re-wiring path and wants this proven first.
- Secret-provider subprocesses do not route through the egress proxy, because the bootstrap floor means it cannot be applied uniformly. Recorded in `DEFERRED.md` with a revisit trigger.
