# lobslaw-encryption

**Decision:** At-rest: bbolt values are sealed with an AEAD chosen at runtime per record, in a versioned envelope: magic(4) | alg(1) | nonce | ciphertext+tag. AlgAESGCM (AES-256-GCM) is preferred where the CPU accelerates AES; AlgXChaCha20Poly1305 otherwise. Both algorithms are always openable on every node — only the sealing default varies — so a cluster of mixed hardware reads every peer's writes. Legacy unversioned nacl/secretbox values continue to open indefinitely; values upgrade format when rewritten, so there is no migration step. A pkg/crypto.Cipher is constructed ONCE per key and reused: building an AES-GCM AEAD costs an allocation plus key expansion, which at 10k records is 1.75ms and 12.8MB of waste per query. Cipher.OpenTo(dst, sealed) supports a caller-reused output buffer; Store.ForEach and ForEachPrefix keep one buffer per walk, which is legal because their documented contract already forbids retaining the plaintext past the callback's return. UNCHANGED: rclone crypt as a first-class option on [[storage.mounts]]; mTLS mandatory for all cluster-internal gRPC; JWT default RS256/EdDSA via JWKS with HS256 as a single-node fallback.

## Rationale

Raft+boltdb holds an episodic diary of your life, so plaintext-on-disk remains unacceptable — this changes the cipher, never the requirement. MEASUREMENT that drove it (pkg/crypto/aead_bench_test.go, 6.6KB payload = one VectorRecord, 30 interleaved samples pinned to dedicated cores): nacl/secretbox with a fresh output buffer 9.08us/708 MiB/s; secretbox with a reused buffer 6.93us/928 MiB/s; XChaCha20-Poly1305 reused 2.67us/2.35 GiB/s; AES-256-GCM reused 1.09us/5.78 GiB/s. So AES-GCM is 8.35x and XChaCha20 3.40x versus the previous implementation, and buffer reuse alone is 1.31x. Interleaving mattered: a single -count=30 gave +/-30% because each benchmark saw a different frequency state under the powersave governor; interleaved runs gave +/-1-13%. WHY RUNTIME SELECTION rather than picking one: Go's crypto/aes falls back to a constant-time SOFTWARE implementation without AES hardware, which is slower than ChaCha20 — that is why ChaCha20 exists and why TLS prefers it on mobile. AES-NI is effectively universal on x86-64 since ~2011 but the ARMv8 crypto extensions are OPTIONAL and absent on the Raspberry Pi 4's Cortex-A72, which is exactly the cheap-hardware target. One extra code path buys correct performance on both. WHY THE LEGACY FALLBACK IS NOT OPTIONAL: legacy values begin with a random 24-byte nonce, so ~1 in 2^32 starts with the envelope magic. OpenTo attempts the versioned parse and falls through to secretbox on failure; without that, those records would be permanently unreadable — silent data loss. Pinned by TestCipherOpensLegacyValueThatLooksVersioned. KNOWN LIMIT: AES-GCM's 96-bit nonce carries a birthday bound of roughly 2^32 sealed values per key. Unreachable for a personal deployment, documented on the AlgAESGCM constant rather than left to be discovered. MEASURED EFFECT end to end (internal/memory/search_bench_test.go, pinned, n=8, p=0.000): vector recall at N=10000 went 130.9ms -> 47.6ms (-63.7%) and 66.7MB -> 442KB allocated (-99.3%); the decrypt-only scan went 93.1ms -> 15.2ms (-83.7%). At N=1000000 a query went 10.88s -> 5.17s and 6.35GB -> 34.6MB. Combined with the top-K/narrow-decode change (PR #21) the cumulative figures versus the previous implementation are -73% latency and -99% allocation, and allocation no longer scales with corpus size.
