# lobslaw-retrieval-raft-only

**Decision:** All retrieval indexes and derived structures live in the Raft-replicated store. NO external vector database, NO pluggable VectorStore vtable, NO sidecar. That principle is unchanged and is reaffirmed. CORRECTED 2026-08-21: the previous version named four buckets and a prefilter as though they existed. They do not. BucketTermPostings, BucketDocStats, BucketVectorBands and BucketEmbedOutbox each have ZERO references in main, and there is no simhash anywhere in the tree. What retrieval actually is today: vector search is a linear scan over BucketVectorRecords computing cosine per record, with a lexical fallback used whenever no embedder is configured or a query cannot be embedded, and a recency weight applied to the score before ranking. There is no approximate prefilter, no inverted index and no outbox. The SimHash band design remains the intended answer to the measured problem and is retained as a PLAN, not a description. The rule that every derived index must be built inside FSM.Apply for the record's own log entry, never via a second raft.Apply, and must be reproducible byte-identically from a snapshot on every replica, applies to any such index when it is built.

## Rationale

The rejection of qdrant/pgvector/lancedb still holds on all four original grounds. What changed is honesty about status. A decision that describes unbuilt structures in the present tense is worse than one that says nothing: it is read as a map of the code, so a reader looking for BucketVectorBands concludes the prefilter exists and the scan cost is already solved. It is not. The measurement stands and is unaddressed — search_bench_test.go at D=1536 showed ~12.5us and ~13.9KB PER RECORD PER QUERY, so N=10000 is ~125ms and ~139MB per user message, with secretbox decrypt ~71% and proto.Unmarshal ~20%. The arithmetic is the smallest component, which is why the prefilter must avoid the DECRYPT rather than the maths, and why bands belong in the key space.

## Details

CORRECTED 2026-08-30. The 2026-08-21 version closed by arguing this decision was an outlier, on the grounds that lobslaw-memory-merge-architecture names FindClusters, Adjudicator, Reranker and Summarizer and 'all four are real (58, 28, 8 and 51 references)'. That check counted references, not behaviour, and was wrong on two of the four — making the same error this decision exists to correct, in the sentence claiming it was not a pattern.
Reranker was never implemented. The 8 references were role-name plumbing: a Role constant, a fallback branch, a provider selected for it at boot, and list_providers advertising 'reranker (memory rerank)' to the model. No reranking code existed anywhere. Removed 2026-08-30, along with the [compute.roles] reranker config field, which let an operator configure a provider that was then never called.
Adjudicator exists as an interface with one implementation, AlwaysKeepDistinctAdjudicator, which returns KeepDistinct unconditionally. SetAdjudicator has no non-test caller. So mergePhase runs, adjudicates every cluster as keep-distinct, tags them with conflict-cluster and supersedes-chain metadata that nothing reads, and does nothing. Real as a stub, not as behaviour.
FindClusters and Summarizer are genuinely built and running.
The lesson is the method, not the count: a reference count cannot distinguish a symbol that runs from one that is only named. Verifying a decision means finding the call path from something that executes.
