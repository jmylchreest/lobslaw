# existing-convention-discovery

**Decision:** Read before you write: inspect sibling files, committed tool configuration, and contributor documentation to establish the local conventions, and derive the conventions from what the repository actually does rather than from what its stack usually does.

## Rationale

Conventions are observable facts about a repository, not something to be guessed from the language. Two Python services can differ on layout, typing strictness, test style, and error handling, and being wrong about which one you are in produces code that reviews badly despite being individually defensible. Reading two or three neighbouring files is far cheaper than a review cycle spent on style, and the committed configuration tells you exactly which rules are enforced rather than which ones are fashionable.

## Details

Before the first edit: read the file you are changing in full plus two or three of its closest siblings; read the repository's contributor guide (CONTRIBUTING.md, CLAUDE.md, AGENTS.md, docs/) and its recorded aide decisions and memories; enumerate the committed tool configuration (.editorconfig, linter and formatter config, type-checker settings, pre-commit hooks, task runner files, CI workflows). Use `aide survey` and the code-index tools to find the existing implementation of the pattern you are about to add — the second instance of something should look like the first. Match what you find on: file and directory naming, module size and splitting, import ordering and grouping, error construction and propagation, logging, dependency wiring, and test placement.
