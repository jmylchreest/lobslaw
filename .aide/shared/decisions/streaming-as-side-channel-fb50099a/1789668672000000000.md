# streaming-as-side-channel

**Decision:** Token streaming is a transport detail inside LLMClient, never a second turn implementation

## Rationale

When a caller sets OnDelta the client reads the response incrementally, hands out text as it arrives, and assembles the same *ChatResponse. The tool-call loop, the failover chain, budget accounting and tool reassembly are untouched and cannot tell which transport ran. A streaming variant of the whole loop would have meant a second copy of all four. Two things fail silently without care: stream_options.include_usage must be set or a streamed turn carries no usage block and silently costs zero while the budget appears to count, and tool calls arrive as index-keyed fragments that must be reassembled by index rather than appended.

## Details

The same reasoning as R33's 'one turn-runner, N callers': the expensive thing is not the feature, it is the second copy of the invariants. The transport boundary is the one place where streaming is expressible, which is why the SSE handler above it can be a thin relay — and why its own bugs (an unguarded writer, an absolute WriteTimeout killing turns over 60s) were handler bugs rather than turn bugs.
