# turn-bot-resolution-order

**Decision:** A turn's bot is resolved before turn.Identity is built, not during fillDefaults

## Rationale

Bots were a console-only feature by accident: five code paths build a turn and only the console set BotID, so every channel ran the pre-bot assistant. Resolution belongs in one place so a channel added later cannot forget it. It must happen BEFORE the identity is stamped: the first version resolved inside fillDefaults, which runs after turn.WithIdentity, so the turn got the coordinator's soul and tool list while every bot tool refused it with 'no bot is taking this turn' — fillDefaults reads req.Bot, the tools read the identity. The identity cannot simply move later because passive recall inside fillDefaults needs it to scope which memories it may read.

## Details

Both entry points into the loop do this, not just the first: RunToolCallLoop and ResumeFromConfirmation each resolve the bot and then Tighten the budget to its caps before stamping identity. A resumed turn is the same turn — approving a confirmation must not be the way a bot gets the node's allowance instead of its own. A test that asserts req.BotID rather than the stamped identity passes while this is broken, because BotID is what the caller sets and the identity is what the callee reads.
